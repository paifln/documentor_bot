# Documentor — материалы к защите

Этот файл — шпаргалка для защиты проекта. Не для пользователей бота, а для
вас: что говорить, что показывать, на какие вопросы комиссии как отвечать.

---

## 1. Что сказать во вступлении (30 секунд)

> «Documentor» — Telegram-бот для Makhambet University, который
> автоматически проверяет курсовые и дипломные работы (.docx) по двум
> направлениям: формальное оформление (поля, шрифт, интервалы, структура,
> список литературы) и содержание текста (грамматика, стиль, логика
> изложения) с помощью AI. Ключевая архитектурная идея: **всё, что можно
> проверить программно со стопроцентной точностью, проверяется кодом; AI
> используется только там, где нужно понимание смысла**. Бот поддерживает
> три языка интерфейса — казахский, русский, английский.

## 2. Архитектура (что рисовать на доске / показывать на слайде)

```
Telegram
   │  (пользователь отправляет .docx)
   ▼
 Bot (aiogram, long polling)  ──ставит задачу──▶  Redis (очередь arq)
   │                                                     │
   │ быстрый ответ пользователю,                         ▼
   │ ничего тяжёлого                              Worker (отдельный процесс)
   ▼                                                     │
PostgreSQL/SQLite ◀───────────────── пишет результат ────┤
                                                          │
                                            ┌─────────────┴─────────────┐
                                            ▼                           ▼
                                     DOCX Parser                  Rule Engine
                                  (python-docx + lxml)      (9 детерминированных
                                            │                  валидаторов)
                                            ▼                           │
                                      AI Analyzer  ◀── LLMProvider ─────┘
                                   (chunking, JSON-схемы)   (OpenAI/DeepSeek)
                                            │
                                            ▼
                                    Aggregator + Scoring
                                            │
                                            ▼
                                     PDF-отчёт (ReportLab)
```

**Почему бот и обработка документа — разные процессы (bot vs worker)?**
Разбор .docx, работа с AI и генерация PDF — тяжёлые и небыстрые операции.
Если делать это прямо в обработчике Telegram-сообщений, бот «зависнет» для
всех остальных пользователей на время проверки. Поэтому бот только
принимает файл и ставит задачу в очередь (Redis), а отдельный процесс
(worker) её выполняет и сам присылает результат в чат.

**Почему очередь на arq, а не Celery/RQ?** Весь проект написан на
`async/await` (aiogram 3, FastAPI, асинхронный HTTP-клиент к LLM). arq —
единственная из трёх asyncio-нативная, то есть job-функции — обычные
`async def`, без блокирующих вызовов и без моста между sync- и
async-мирами, который потребовался бы для Celery/RQ. Плюс она использует
тот же Redis, который уже нужен для очереди — не вводит лишнюю инфраструктуру.

## 3. Ключевые технические решения — на случай вопросов

| Вопрос комиссии | Ответ |
|---|---|
| Как проверяется оформление? | Библиотека `python-docx` читает XML документа (OOXML) напрямую: реальные поля, размеры шрифта, межстрочный интервал — а не «на глаз». Там, где `python-docx` не даёт нужных данных, используется `lxml` для прямого разбора XML. |
| Почему не доверяете AI проверку полей/шрифта? | AI может «увидеть» то, чего нет, или пропустить реальную ошибку — вероятностная модель не даёт 100% гарантии на измеримых параметрах. Поле в 20мм вместо 30мм — это факт, а не мнение, поэтому это код, не LLM. |
| Как AI-часть защищена от галлюцинаций? | Модель обязана отвечать строго в формате JSON, который валидируется через Pydantic-схемы. Если ответ не проходит валидацию — он отбрасывается, а не показывается пользователю. В промптах прямо прописано: «если не уверена — снижай confidence, а не выдумывай ошибку». |
| Как работает с казахским языком? | Отдельная задача — большинство систем такого рода ищут заголовки по названию стиля Word («Heading 1»), которое в казахской/русской версии Word отображается по-другому («Тақырып 1», «Заголовок 1»). Мы читаем языконезависимый XML-атрибут (`w:outlineLvl`, `w:styleId`), который не зависит от локализации интерфейса Word. Плюс распознавание разделов (Кіріспе/Введение/Introduction) идёт по регулярным выражениям на трёх языках одновременно. |
| Как проверяется список литературы? | Считается количество записей, ищутся дубликаты, проверяется наличие ссылок в тексте вида `[1]`, `[2, 3]`. Система **не** утверждает, что источник существует — только считает и сверяет формальные признаки. |
| А если студент попытается загрузить вирус/подделать файл? | Проверяется реальная сигнатура ZIP/OOXML-архива (не по расширению файла), обязательные внутренние части документа, защита от zip-slip/path traversal, лимит размера. Файл никогда не «выполняется», только читается. |
| Что с приватностью данных? | Файл хранится только во временной директории под случайным именем, автоматически удаляется после обработки и по истечении срока хранения. В БД сохраняются только результаты проверки (баллы, короткие цитаты до 200 символов), а не полный текст работы. |
| Почему архитектура модульная, а не один скрипт? | Каждый слой (парсинг, правила, AI, оценка, отчёты, Telegram-интерфейс) — отдельный, независимо тестируемый модуль. Это позволяет, например, заменить LLM-провайдера (OpenAI → DeepSeek → Anthropic) без переписывания остального кода — есть абстракция `LLMProvider`. |
| Что будет, если AI-сервис недоступен? | Проверка не падает целиком — пользователь получает результаты по оформлению и структуре, и явно видит пометку «AI-анализ выполнен частично». |
| Как добавить новый вуз или новые требования? | Требования — это YAML-файл (`rules/presets/*.yaml`), не код. Администратор создаёт файл с нужными полями/шрифтом/структурой — система подхватывает его после перезапуска, без единой строки Python. |
| Какая оценка (scoring) используется? | Взвешенная система по категориям (Оформление/Структура/Язык/Стиль/Содержание), веса настраиваются в том же YAML-пресете и должны суммарно давать 100. Каждая найденная проблема снижает баллы категории пропорционально серьёзности (critical/error/warning), а для AI-находок — ещё и пропорционально её уверенности (confidence). |
| Что не реализовано? (не бойтесь этого вопроса — честный ответ сильнее) | Проверка на плагиат (есть только интерфейс `SimilarityChecker`, реализации нет — бот никогда не заявляет, что проверяет на плагиат), веб-интерфейс/личный кабинет, пакетная проверка группы работ (ZIP с несколькими файлами), экспорт в Excel/CSV. Всё это заложено в архитектуре (отдельные модули/интерфейсы), но не реализовано в MVP — это сознательное решение, а не недосмотр. |

## 4. Сценарий демонстрации (что делать вживую)

1. `/start` → показать выбор языка (🇰🇿/🇷🇺/🇬🇧) → выбрать язык.
2. Показать главное меню → «📄 Проверить работу» → выбрать тип работы
   (курсовая/дипломная).
3. Отправить заранее подготовленный `.docx` с **намеренными ошибками**
   (неправильный шрифт, отсутствует раздел «Заключение», список литературы
   короче требуемого) — чтобы демонстрация показала реальные найденные
   проблемы, а не пустой отчёт.
4. Показать прогресс-сообщения (этапы: структура → оформление → текст →
   AI → отчёт) — это наглядно демонстрирует, что происходит не «чёрный
   ящик», а понятный пайплайн.
5. Показать итоговое сообщение с баллом и кнопками (Результат/Ошибки/
   Рекомендации/PDF/Новая проверка).
6. Открыть PDF — обратить внимание комиссии на то, что кириллица и
   казахские буквы отображаются корректно (это специально решённая
   техническая проблема, стоит подчеркнуть).
7. Показать «📋 История проверок».
8. Если есть время — `/admin_stats` (нужны права администратора,
   `ADMIN_IDS` в `.env`) — показать статистику по системе.

**Подготовьте заранее 2 файла**: один «плохой» (с ошибками — для основной
демонстрации) и один «почти правильный» (для контраста, показать высокий
балл). Так комиссия увидит, что система действительно различает качество,
а не просто выводит фиксированный текст.

## 5. Если что-то пойдёт не так во время защиты

- **Бот не отвечает** → проверить, что оба процесса запущены: бот
  (`python -m app.main` / `docker compose logs bot`) и воркер
  (`arq app.worker.WorkerSettings` / `docker compose logs worker`).
- **Зависло на «⏳ Начинаю проверку…»** → скорее всего Redis не поднят
  или воркер не запущен — см. выше.
- **AI-часть пустая / «AI-анализ выполнен частично»** → это НЕ баг, а
  штатное поведение системы при недоступности LLM-провайдера (например,
  кончилась квота DeepSeek/OpenAI) — **можно смело объяснить это
  комиссии как демонстрацию отказоустойчивости**: «система не падает
  целиком, если недоступен внешний AI-сервис — это заложено намеренно».
- **PDF не открывается / шрифт квадратами** — только если вы запускаете
  вне Docker и на машине физически нет ни одного TTF-шрифта с кириллицей
  (крайне маловероятно на Windows — там всегда есть Arial/Times New Roman).

## 6. Итоговый список реализованного (для отчёта/презентации)

Реализовано полностью и работает:
- Telegram-бот с выбором языка интерфейса (kk/ru/en)
- Приём и валидация `.docx` (безопасность: сигнатура, MIME, размер, защита от path traversal)
- Парсинг документа: поля, страница, шрифты, интервалы, отступы, заголовки
- Языконезависимое определение структуры (казахский/русский/английский)
- 9 детерминированных валидаторов правил + YAML-пресеты требований
- AI-анализ текста через провайдеро-независимую абстракцию (`LLMProvider`)
- Строгая валидация AI-ответов через Pydantic-схемы
- Chunking длинных документов, бюджетирование токенов
- Scoring с настраиваемыми весами
- PDF-отчёт с поддержкой кириллицы/казахского на выбранном языке
- История проверок, роль администратора
- PostgreSQL/SQLite + Alembic-миграции
- Docker (bot/worker/postgres/redis)
- Unit- и интеграционные тесты с mock LLM-провайдером

Сознательно не реализовано (заложено в архитектуре как точки расширения):
- Проверка на плагиат (только интерфейс `SimilarityChecker`)
- Веб-интерфейс / личный кабинет (есть только базовый FastAPI-эндпоинт)
- Пакетная проверка группы работ
- Экспорт в Excel/CSV
